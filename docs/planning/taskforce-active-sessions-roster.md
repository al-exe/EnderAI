# Taskforce — Active Sessions Roster

*Plan (2026-06-12). Follow-on to the EM quickstart fix (PR #127). Derived from a live debugging session of `docs/testing/taskforce-em-quickstart.md`.*

## Context

**The EM ask, restated.** "He mostly wants to be able to open multiple Claude instances, and have those Claudes know what's going on between [them] so [he] doesn't need to re-explain across terminals or VMs." Picture a tmux session with 4 Claudes open — frontend, payments, backend, tracking — not necessarily working on the *same* task right now, but each would benefit from knowing **what the other three are currently doing**, so they can interface quickly when they need to.

**Why this is simpler than "shared live doc."** An earlier framing of this (multiple agents converging on and PATCHing one shared document) introduces write contention and a doc-ownership question. The simpler version: **each agent keeps writing its own document** (this already happens — `active_document_id` pinning + checkpoint hook), and we add one new thing — **on every prompt, each agent also sees a short roster of what its currently-active siblings are working on**, with pointers into the library for full detail. No shared writes, no merge logic.

## Current state (what already exists — do not rebuild)

- **Per-session document**: `taskforce-user-prompt-submit.sh` stashes `active_document_id` for the session (`~/.taskforce/<session_id>.active`); `taskforce-post-tool-use.sh` (checkpoint, every `CHECKPOINT_EVERY` tool calls) and `taskforce-stop.sh` (final) both PATCH that document via `POST /v2/taskforce/observe`.
- **Per-prompt discovery**: `taskforce-user-prompt-submit.sh` already calls `POST /v2/taskforce/discover` on *every* prompt (not just session start) and injects a `─── Related prior work (Taskforce) ───` block + `[Taskforce] N related doc(s) pulled` banner. **PR #127** fixed two bugs in this path (422s from malformed transcript content, and a discover `min_score` that filtered out good-but-not-great matches).
- **Session bookkeeping**: `TaskforceSessionArchive` (`app/models.py:1434`) has `session_id`, `actor_id`, `organization_id`, `cwd`, `branch`, `repo`, `started_at`, `ended_at` (nullable — set at `Stop`). No `last_seen_at` / heartbeat field yet.
- **Document summaries**: the backend's summarizer already produces multi-sentence `ai_generated_summary` text per document (observed in testing: *"User documented staging Postgres DSN rotation schedule (14-day cycle) and runbook location (ops/db-rotation.md). Created db-note.md file to capture this operational detail for future reference."*) — this is already "more than one line" and is what the roster entry should reuse, not a new summary path.

## Design

### 1. New signal: `last_seen_at` heartbeat

Add `last_seen_at: datetime` to `TaskforceSessionArchive`, updated by **`taskforce-user-prompt-submit.sh` on every prompt** (cheap — it already makes a network call every prompt) via a small new field on the `/discover` request, e.g. `heartbeat: true` or simply let `/discover` always touch `last_seen_at` for the given `session_id`.

Why not rely on checkpoint cadence alone: `PostToolUse` checkpoints fire every *N tool calls*, so a session that's mid-thought (reading, planning, no tool calls yet) could look stale even though the user is actively in that terminal. A prompt-level heartbeat is the more accurate "is a human actually at this terminal" signal, decoupled from tool-call cadence.

### 2. Roster in the discover response

`POST /v2/taskforce/discover` response gains `active_sessions: []`, alongside the existing `matches`:

```jsonc
{
  "matches": [ ... ],          // unchanged — topical document matches
  "active_sessions": [
    {
      "session_id": "...",
      "cwd": "/home/alexlee/dev/EnderAI-frontend",
      "branch": "feature/checkout-redesign",
      "repo": "EnderAI-frontend",
      "active_document_id": "...",
      "title": "Checkout redesign — cart summary component",
      "summary_markdown": "<full multi-sentence ai_generated_summary>",
      "last_seen_at": "2026-06-12T14:02:11Z",
      "minutes_ago": 6
    }
  ]
}
```

Query: `taskforce_session_archive` where `actor_id = <me>`, `session_id != <self>`, `ended_at IS NULL`, `last_seen_at >= now() - 8h`, ordered by `last_seen_at DESC`, **capped at top 5**. Join each row's `active_document_id` → `V2Document` for `title` + `ai_generated_summary`.

### 3. Richer roster entries ("more than one line")

Use the document's existing `ai_generated_summary` in full (it's already 2-4 sentences), not a truncated title. This costs nothing extra to produce — it's already generated by the checkpoint/final summarizer pass. Each roster entry = title + full summary + `cwd`/`branch`/`repo` + `minutes_ago`, so a reading agent can judge both *what* the sibling is doing and *how current* that is.

### 4. Hook-side rendering

`taskforce-user-prompt-submit.sh` adds a second preamble block (only when `active_sessions` is non-empty):

```
─── Active sibling sessions (Taskforce) ──────────────
[EnderAI-frontend · feature/checkout-redesign · 6m ago]
Checkout redesign — cart summary component
<2-4 sentence summary>

[EnderAI-backend · main · 41m ago]
Payments webhook idempotency fix
<2-4 sentence summary>
─── End active sibling sessions ──────────────────────
```
Plus a banner addition: `[Taskforce] 2 active sibling sessions · EnderAI-frontend (6m ago), EnderAI-backend (41m ago)`.

## Staleness — beyond a flat 8h cutoff

8h as a *ceiling* is reasonable (covers "stepped away for lunch," excludes "left running overnight"), but a flat cutoff alone has two failure modes: (a) a session opened 7h59m ago with one checkpoint looks identical to one from 2 minutes ago, and (b) a user who slowly accumulates many short-lived sessions in a day could still hit 5+ "active" entries that aren't all relevant *right now*.

Refinements, roughly in order of value:
- **Surface `minutes_ago` in the roster itself** (done above) rather than a binary in/out — let the *consuming* agent weigh a 6-minutes-ago sibling more than a 7-hours-ago one. This is cheap and removes most of the need to get the cutoff "right."
- **Hard cap by count (top 5 most recent), not just time** — bounds the roster size regardless of how many sessions accumulate; naturally self-prunes as new sessions push old ones out, independent of the time window's exact value.
- **Exclude cleanly-ended sessions outright** (`ended_at IS NOT NULL`) — the 8h window only needs to catch "forgot to `/exit`" / crashed sessions, not properly-closed ones. This means the window can be generous (8h) without much cost, since it's a backstop, not the primary filter.
- **Repo/cwd affinity (later)**: sort or group by "same repo as me" vs "elsewhere" — a sibling working in the same repo is more likely to produce an interface change you care about than one in an unrelated project. Defer unless the flat recency-sorted list proves noisy in practice.
- **Cross-user / org visibility (later, ties to existing `visibility: organization` model)**: today scope to `actor_id = me` (same person, multiple terminals/VMs, matching the EM's literal ask). Cross-teammate awareness is a natural v2 but reuses the existing org-visibility plumbing from the empty-cell work — don't build it now.

## Open questions

- Should the heartbeat be its own lightweight endpoint (`POST /v2/taskforce/session/heartbeat`) vs. piggybacking on `/discover`? Piggybacking avoids a new round-trip per prompt; a dedicated endpoint is cleaner if `/discover` ever needs to be cacheable/idempotent.
- `active_document_id` may be `null` early in a session (before the first checkpoint creates a doc) — roster entry should degrade gracefully (e.g., show `cwd`/`branch` + "just started" instead of omitting the sibling).

## Sequencing

1. Migration: add `last_seen_at` (nullable, indexed) to `taskforce_session_archive`.
2. Backend: `/discover` updates `last_seen_at` for `session_id` (heartbeat) and returns `active_sessions` (query above).
3. Hook: `taskforce-user-prompt-submit.sh` renders the new preamble block + banner segment.
4. Test: 3-4 concurrent `claude` sessions in different `cwd`s under the same user; confirm each sees the others within ~1 prompt cycle, roster shrinks as sessions `/exit` or age past 8h.

## Frontend surface

**Why this matters beyond the hook.** The roster gives *agents* cross-instance awareness; the frontend version gives the *human* the same view — "what are my 4 open Claudes doing right now," glanceable without alt-tabbing through terminals. It's also the natural place to demo this to an EM (a live dashboard reads better than a terminal banner).

### Placement: presence rail on `/v2/library`

`EnderAI-frontend/src/routes/v2/library.tsx` already renders `LibraryRecentReel` (recently-touched documents) right above the folder/file grid (`library.tsx:838`). Add a new **`ActiveSessionsRail`** component directly above it, in the same horizontal-reel style:

- One small card per active session: repo/cwd + branch chip, document title, 2-3 line `ai_generated_summary` clamp, and a relative-time badge (`formatRelativeTime`, already used by `AgentSessionCard`/`LibraryRecentReel`).
- A small presence dot: green/pulsing if `minutes_ago < 5` ("live"), gray otherwise ("idle, still open").
- Click → `/v2/library/$documentId` (existing route) for the full document.
- **Empty state: hide the rail entirely** when `active_sessions` is empty (single-session users, or right after the only session exits) — same pattern as the `documents.length > 0` guard around `LibraryRecentReel`.

### New read endpoint

Reuse the backend query from the roster design (§2), but as its own endpoint rather than folded into `/discover`'s response, since the frontend isn't running a discover-style query:

```
GET /v2/taskforce/active-sessions
→ { active_sessions: [ { session_id, cwd, branch, repo, active_document_id, title, summary_markdown, last_seen_at, minutes_ago } ] }
```

Same underlying query (`actor_id = me`, `ended_at IS NULL`, `last_seen_at >= now() - 8h`, top 5 by recency) — factor it into a shared helper so the `/discover` roster and this endpoint can't drift.

### Freshness on the frontend

Polling fits the existing patterns (`staleTime: 30_000` on `AgentSessionCard`'s query) — no websockets needed. `refetchInterval: 30_000` keeps the presence dots and relative-time labels current without much load, since this is a small, capped (≤5 row) query.

### Later ideas (don't build now)

- Cross-link from `/v2/agents/$slug` — if a sibling session's routed specialist matches the agent being viewed, show "live session in progress" on `AgentProfileCard`.
- Org-wide presence (which teammates have active sessions right now) once cross-user visibility (§"Staleness" notes) is built — natural fit for a future team-dashboard view, not this iteration.
