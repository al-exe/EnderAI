Stripe webhook idempotency strategy

Inbound Stripe webhooks are deduped via a stripe_webhook_event WAL table keyed on event_id + is_test_mode. Baseline replay coverage exists; newer event-specific paths still need targeted regression tests.

Summary
Details
Split

Stripe documents webhook redelivery as "best-effort up to 3 days," but the real-world failure mode is more aggressive than that. During provider-side recovery from regional outages the same event.id can arrive 2–5 times within minutes — the 8-second timeout on a non-2xx response is only the minimum retry trigger. Any handler that mutates customer state has to assume redelivery.

Before this incident, billing.py trusted that each event would be delivered once. Each handler — checkout completion, subscription update, invoice paid — was idempotent against Stripe's outbound API using event.id as the Idempotency-Key header. That covered our outbound calls (refunds, voided charges) but did nothing about inbound side effects (entitlement writes, invoice rows, tier transitions). When the same event arrived twice, fulfillment ran twice.

Incident · 2026-04-11

At 14:37 UTC, Stripe's us-west-2 had a partial outage. Their retry queue drained when service recovered around 15:10 UTC. Over the next ~3 minutes we processed customer.subscription.updated events twice for ~30 Pro upgrades.

Each customer was charged a second invoice for the same upgrade. Refunds went out the next day; the root cause was that we had no inbound idempotency. §3 · postmortem

The fix · WAL table at the route boundary

Decision: dedupe at the route boundary, not inside each handler. A small write-ahead log (the stripe_webhook_event table) records every inbound event before any business logic runs. The handler then becomes a pure function of "first time we've seen this event_id." 

-- stripe_webhook_event: the dedupe boundary
CREATE TABLE stripe_webhook_event (
  event_id      text      PRIMARY KEY,
  is_test_mode  boolean   NOT NULL,
  received_at   timestamptz NOT NULL DEFAULT now(),
  outcome       text      NOT NULL  -- 'fulfilled' | 'duplicate' | 'failed'
);

-- In the route, before dispatch:
INSERT INTO stripe_webhook_event (event_id, is_test_mode, outcome)
VALUES ($1, $2, 'pending')
ON CONFLICT (event_id) DO NOTHING
RETURNING xmax = 0 AS is_new;

If the INSERT returns is_new = true, the handler dispatches. If it doesn't, we log the duplicate and return 200 OK with no fulfillment side effects. The primary key gives us correctness under concurrent replays — Stripe will sometimes deliver the same event from two regions within milliseconds and Postgres serializes the conflict for us.

The choice of (event_id, is_test_mode) as the natural key matters: live and test events share an ID space in Stripe's API, and we have to keep them dedupable independently. Details on the test-mode collision case live in §4 · test mode.

What still needs coverage

Baseline replay coverage exists for the four oldest handlers — checkout, subscription updated, invoice paid, payment failed. Newer event-specific fulfillment paths (the entitlement bridge, the seat-count reconciler, the dunning state machine) still need targeted regression tests that simulate redelivery and assert "fulfillment runs exactly once."
